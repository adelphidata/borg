# Networking & Deployment

Borg ships as a single binary, but a useful install almost always means
two or more devices talking to one borgd. This doc covers the four
deployment surfaces that make that possible:

- **mDNS / Bonjour announcement** — LAN peers discover borgd without
  hand-typing hostnames.
- **Tailscale peer enumeration** — tailnet peers do the same over WG.
- **Tunneling** — `cloudflared` / `ngrok` / `tailscale` / custom commands
  expose the gateway publicly.
- **launchd / systemd lifecycle** — `install / start / stop / status /
  restart / uninstall`, with the manager's view folded into status.

A fifth section covers the APNs push pipeline, which wakes paired iOS
clients when an inbound gateway message arrives.

## Service lifecycle

The CLI:

```
borg service install     # write plist / unit file
borg service start       # launchctl start / systemctl ... start
borg service stop        # launchctl stop  / systemctl ... stop
borg service restart     # stop + start
borg service status      # see below
borg service uninstall   # remove plist / unit file
```

`status` combines two facts that historically rendered as the same
"not running" string:

1. **UDS reachability** — can the CLI open `~/.borg/run/borgd.sock`?
2. **Platform manager state** — what does `launchctl list` / `systemctl
   is-active` say about the borgd unit?

The matrix renders eight cells into seven runbook-bearing messages
(see `crates/interface/src/borgd_launcher.rs::format_service_status`).
The diagnostic ones to recognize:

| State | Means |
|---|---|
| `running` | Healthy: UDS up, manager reports active. |
| `running (orphaned — installed unit reports inactive)` | UDS up, but the manager thinks the unit is stopped — usually means you spawned `borgd` by hand after the service was uninstalled, or KeepAlive hasn't kicked in. Re-install to re-link. |
| `running (direct spawn — no installed unit)` | UDS up, no plist/unit on disk — fine for dev, but on logout / reboot nothing brings it back. Run `borg service install`. |
| `loaded but unreachable (manager reports active but UDS down — daemon is wedged)` | The unit is loaded and the manager believes it's running, but borgd isn't answering. Try `borg service restart`. |
| `stopped (unit installed; start with 'borg service start')` | Idle but installed. |
| `not installed (install with 'borg service install')` | No unit on disk and no UDS. First-time setup. |
| `not running` | Probe failed (e.g. `launchctl` missing from PATH). Opaque fallback. |

`status` then prints the daemon's own version / uptime / live sessions /
LLM provider / task counts if the UDS was reachable.

### Where the unit files live

- macOS: `~/Library/LaunchAgents/com.borg.daemon.plist` (user scope, the
  default). `borg service install --system` writes to
  `/Library/LaunchDaemons/com.borg.daemon.plist`.
- Linux: `~/.config/systemd/user/borg.service` (user scope), or
  `/etc/systemd/system/borg.service` (system scope).

`--secure` swaps in the secure-template variant that pins KEK backend to
`gnome-keyring` (Debian/Ubuntu) and fires the one-time
`secure_headless_setup` posture milestone. The plist / unit templates
themselves are not regenerated by start/stop — only `install`.

## mDNS announcement + SAN auto-expansion

Disabled by default. To enable:

```
borg settings set discovery.mdns_enabled true
```

What happens at daemon start when `discovery.mdns_enabled = true` and
borgd is bound to a non-loopback address:

1. **Server cert SAN expands** to include `gethostname()` and
   `<hostname>.local`, in addition to anything from
   `BORG_DAEMON_TLS_SAN`. DNS is case-insensitive; hostnames are
   lowercased before insertion. See
   `crates/borgd/src/auth/san.rs::derive_server_san_with_mdns`.
2. **mDNS announcer publishes** `_borgd._tcp.local.` with the borgd
   port. Instance name defaults to `<hostname>-borgd`, overridable via
   `discovery.mdns_instance_name`.
3. **TXT records** carry `v=1`, `fp=<sha256 of server cert>` (first 16
   hex chars), and `node=<node_id>`. A LAN peer pairing against the
   announced instance can pin the fingerprint before its first
   handshake.

If `mdns_enabled = false`, or the bind is loopback, neither the SAN
expansion nor the announce runs. Loopback-only is still the right
default for a single-machine install — mDNS over loopback is
meaningless, and the SAN auto-append would only add noise.

### Browsing a borgd from another machine

```
# macOS
dns-sd -B _borgd._tcp local.
dns-sd -L <instance-name> _borgd._tcp local.

# Linux
avahi-browse -r _borgd._tcp
```

`borg device pair --discover` (CLI) shells out to both mDNS and
`tailscale status` to surface a single picker UI rather than asking the
operator to type a hostname.

## Tailscale peer enumeration

Enabled by default (`discovery.tailscale_enabled = true`). At pairing
time `borg device pair --discover` shells out to `tailscale status
--json`, parses `Self.DNSName` + `Peer.<id>.DNSName` + `TailscaleIPs`,
and merges the result into the picker.

If `tailscale` is not on PATH, the call errors with an actionable
message containing the install URL — the existing pairing flow keeps
working without it.

No long-lived `tailscale` subprocess runs. The borgd daemon does not
hold an open connection to the tailnet; it just calls the CLI on demand.

## Tunneling

The four supported providers all wrap an external binary that's assumed
already on PATH. Missing binaries surface as a
`TunnelError::BinaryMissing` with the install URL, never a generic
"No such file or directory."

| Provider | Binary | Required config | Install URL |
|---|---|---|---|
| `cloudflare` | `cloudflared` | `tunnel.cloudflare.token` | https://github.com/cloudflare/cloudflared/releases |
| `ngrok` | `ngrok` | `tunnel.ngrok.auth_token` (+ optional `tunnel.ngrok.domain` for paid plans) | https://ngrok.com/download |
| `tailscale` | `tailscale` | none in borg config — leans on host's `tailscale up` state | https://tailscale.com/download |
| `custom` | operator-supplied | `tunnel.custom.start_command` with `{host}` / `{port}` placeholders | n/a |
| `none` | — | — | — |

### CLI

```
borg tunnel start    # spawn under supervisor; returns public URL
borg tunnel stop     # graceful kill
borg tunnel status   # provider + running + public_url + last_error
```

`borg tunnel start` calls Admin gRPC `TunnelStart`; the daemon spawns
the tunnel under `spawn_supervised` so a crashed `cloudflared` /
`ngrok` is restarted with exponential backoff up to the standard 5-in-
10-min degraded cap.

### Security caveats

- **ngrok auth token** is passed via the `NGROK_AUTHTOKEN` env var to
  the child process, **never on argv**. Same-session local processes
  can read another process's argv via `ps -ef` / `tasklist /v`;
  passing the token on argv would leak it across the same-user
  boundary. The `ngrok_authtoken_passed_via_env_not_argv` test in
  `crates/gateway/src/tunnel/ngrok.rs` is the regression guard.
- **Cloudflare tunnel token** lives in the borg settings table; keep
  the DB file at `~/.borg/borg.db` mode 0600. The token is a sensitive
  credential — anyone with it can route traffic into your tunnel.
- **Tailscale funnel** (`tunnel.tailscale.funnel = true`) exposes the
  service on the public internet via Tailscale's edge. Use `serve`
  mode (`funnel = false`) for tailnet-only exposure. The default is
  `serve`.
- **Custom commands** accept `{host}` / `{port}` placeholders and a
  `url_pattern` substring used to scrape the public URL from stdout.
  If `url_pattern` is `None`, the operator must surface the URL
  out-of-band; `borg tunnel status` falls back to `health_url` as a
  placeholder.

### Pipe drain — why it matters

Each tunnel provider wraps its child process in `TunnelProcess { child,
_pipe_drain }`. The `_pipe_drain` task is a `tokio::spawn` that reads
the child's stdout into `tracing::trace!`. It MUST stay alive for the
process's lifetime:

- If the task drops, the OS pipe closes and the child receives SIGPIPE
  on its next write.
- If the task never reads, the pipe buffer (~64 KiB) fills and the
  child blocks indefinitely on its next write.

Both failure modes look like "the tunnel works for a minute then dies."
Do not refactor the drain task out without keeping the read pump alive
somewhere else.

## APNs push pipeline

**Status: surface + stub verifier.** The DB schema, gRPC RPCs, push
trigger, and 410-invalidation paths are in place. The App Attest
verifier returns `AttestError::NotImplemented` so `RegisterDevice`
rejects every request until the verifier lands — see the roadmap entry
under "APNs App Attest verifier" for the follow-up work.

Disabled by default. To enable:

```
borg settings set apns.enabled true
borg settings set apns.bundle_id com.example.borg
borg settings set apns.team_id ABCDE12345
borg settings set apns.key_id ABC123DEF4
borg settings set apns.private_key_p8_path apns.p8   # under ~/.borg/secrets/
```

### Registration flow

1. iOS client calls `Apns.IssueChallenge` over mTLS using its paired-
   device cert. The daemon returns a fresh 32-byte nonce with a
   5-minute TTL keyed on the client cert fingerprint.
2. The client generates an App Attest assertion against that nonce and
   posts `Apns.RegisterDevice` with the assertion + the APNs device
   token Apple handed to it.
3. The daemon verifies the assertion against Apple's App Attest root
   CA (production) or a test CA (cfg(test)), validates the nonce, RP
   ID, counter, and credentialId, then persists a row in
   `apns_device_tokens` keyed on the paired device fingerprint.

The challenge store is in-memory only (`crates/borgd/src/apns/
challenge_store.rs`). A daemon restart clears all outstanding
challenges; the client retries by re-issuing.

### Wake trigger

Gateway message-arrival hook calls `wake_paired_devices(db, &apns_cfg,
recipient)` for any inbound message addressed to a paired sender. The
trigger fetches every active APNs token for `recipient`, asks the
client to send a silent push (`content-available: 1`), and tallies a
`WakeReport { accepted, invalidated, rejected, skipped }`.

APNs 410 (`BadDeviceToken`) responses mark the token row's
`invalidated_at` so subsequent triggers skip it; 400/403 responses
increment the `rejected` counter without invalidating. The `borg
status` snapshot surfaces the last report.

When `apns.enabled = false`, the trigger short-circuits before touching
the DB so a fresh install pays no per-message SELECT cost.

### Database schema

`apns_device_tokens` (migration v3):

| Column | Purpose |
|---|---|
| `id` | Rowid PK. |
| `device_id` | Paired-device fingerprint (UNIQUE — one APNs token per device). |
| `apns_token` | Hex device token from APNs. |
| `bundle_id` | Sanity-check against `apns.bundle_id`. |
| `app_attest_key_id` | Verified App Attest key ID. |
| `app_attest_pub_key_der` | P-256 SPKI DER from the credCert. |
| `registered_at`, `last_push_at` | Timestamps for telemetry. |
| `invalidated_at`, `invalidated_reason` | Set on APNs 410. Active queries filter `WHERE invalidated_at IS NULL`. |

A partial index on `(device_id) WHERE invalidated_at IS NULL` keeps the
hot path single-row.

## Operator runbooks

### "I want LAN multi-device"

```
borg settings set discovery.mdns_enabled true
borg service restart           # re-issue cert with expanded SAN
# on each peer:
borg device pair --discover    # picks the announcing borgd
```

### "I want public access via Cloudflare"

```
# install cloudflared, create a tunnel in the Cloudflare dashboard,
# copy the tunnel token
borg settings set tunnel.provider cloudflare
borg settings set tunnel.cloudflare.token <T>
borg tunnel start              # returns the trycloudflare.com URL
```

### "I want to wake my iPhone"

Today: not yet — the verifier is stubbed. Once it lands:

1. Build + provision the iOS client with the correct bundle ID and App
   Attest entitlement.
2. Enable APNs as above.
3. iOS client pairs (mTLS), calls `IssueChallenge`, posts
   `RegisterDevice` with an App Attest assertion.
4. Inbound gateway messages addressed to the paired sender wake the
   device via silent push.

### "borg service status shows 'loaded but unreachable'"

The manager thinks borgd is running, but it isn't answering on its UDS.
Tail `~/.borg/logs/daemon.err` for the panic / crash loop, then
`borg service restart`. If it recurs, the supervisor will eventually
mark the subsystem degraded — see `docs/daemon-supervision.md`.
